The platform is organized as a pipeline of cooperating Python packages sharing a common `results/` artifact directory and a single `requirements.txt` dependency set: `data_pipeline` generates aggregate training datasets from synthetic or live weather feeds; `ml_models` trains, evaluates, persists, and promotes LightGBM quantile models to a file-based registry in `results/model_versions`; `reporting` imports STEG Prosol snapshots and raw measurements into an immutable history store and computes forecast-vs-actual metrics back into `results`; `api_server` exposes all services (forecast, model retraining, diagnostics, reporting) over FastAPI endpoints backed by an in-process cache and APScheduler jobs; `dashboard` is a self-contained HTML client that optionally connects live to the API for real-time visualization; `results_artifacts` is the shared on-disk contract holding time-series forecasts, model artifacts, evaluation summaries, and Prosol logs consumed by both the API and dashboard. Cross-child communication is therefore file-based (shared `results/` layout) plus HTTP (dashboard ↔ api_server), with no message bus or database at this stage.
